# 페이지 단위 벡터 PDF 내보내기

기존 PDF는 필기까지 포함한 페이지 전체를 1800px JPEG로 저장했습니다. 새 PDF는 같은 `NoteRenderer`가 `PdfDocument`의 Canvas에 필기, 도형, 용지와 글자를 직접 그립니다. 일반 필기 페이지는 전체 페이지 비트맵을 만들지 않으며, 확대 시 필기 경로와 도형의 해상도가 유지됩니다. PNG도 같은 페이지 렌더러를 사용합니다.

## 구조와 메모리

1. 저장소 executor에서 페이지 ID 목록을 얻고 현재 페이지 하나만 읽습니다.
2. **페이지마다 별도 `PdfDocument`**를 만들고 Canvas를 논리 페이지 좌표로 변환합니다. 기존 브러시·필압·기울기·곡선·회전·불투명도·객체 순서를 재사용합니다.
3. 페이지를 끝내고 PDF 임시 파일에 쓴 뒤 native 문서를 닫습니다. 전체 문서의 페이지를 한 `PdfDocument`에 누적하지 않습니다.
4. `PdfPageAssembler`가 페이지의 xref를 읽고 객체 번호·간접 참조·Parent를 최종 문서에 맞게 바꿉니다. 이미지, 압축된 명령, 폰트와 문자열의 실제 바이트는 변경하지 않습니다. 스트림은 길이를 기준으로 64 KiB씩 복사합니다.
5. 마지막에 최종 Pages 트리와 xref를 기록합니다. 취소·오류 시 페이지 임시 파일과 미완성 결과를 삭제합니다.

전체 PDF/자산을 `ByteArray`나 문자열로 읽지 않습니다. 문서 전체에서 유지되는 것은 페이지 ID·객체 위치·페이지 참조이며, 이 메타데이터는 객체 수에 비례합니다. 단일 페이지의 JSON/기하 및 Android의 native PDF 기록 메모리는 별도로 필요합니다.

`PdfDocument`가 한 페이지의 이미지 픽셀을 모두 기록할 수 있으므로, 배경과 표시되는 이미지 객체의 디코딩 크기를 미리 계산합니다. **예상 이미지 픽셀이 24 MiB를 넘는 페이지**는 기존의 이미지 순차 디코딩·해제 방식으로 페이지 하나를 래스터화합니다. 다른 페이지는 계속 벡터로 저장합니다. 이 수치는 전체 앱 힙 또는 native 메모리 상한을 보증하는 수치가 아닙니다.

## 범위와 호환성

| 항목 | 처리 |
| --- | --- |
| 필기·도형·용지·텍스트 | 기존 네이티브 Canvas 렌더러로 직접 PDF 기록 |
| 가져온 PDF 배경 | 기존 해상도에서 래스터화 후 벡터 필기와 합성 |
| 이미지 | 기존 디코딩 해상도를 유지; 이미지 예산을 넘으면 해당 페이지 전체 래스터화 |
| 숨긴 객체·OCR 인덱스 | 기존 렌더러와 동일하게 출력에서 제외 |
| 한글·폰트·알파·회전 | Android가 생성한 폰트/리소스와 순서를 보존 |
| `.ifnote`·SQLite/Room·OCR | 저장 포맷과 처리 경로 변경 없음 |

병합기는 **앱이 직접 생성한 단일 페이지 PDF만** 처리합니다. classic xref, generation 0, Catalog 하나와 flat Pages 하나를 요구합니다. 암호화·증분 저장·xref stream·다중 페이지 입력은 거절합니다. 사용자 PDF를 이 병합기로 직접 읽지 않습니다. `PdfRenderer`가 배경으로 렌더링한 뒤 Android가 새 페이지를 생성합니다. 원본 PDF 텍스트 레이어/검색/링크/주석을 그대로 보존하는 기능은 이번 범위에 포함되지 않습니다.

PR #7의 최신 브러시 렌더러를 사용하므로 기준은 `codex/ocr-4.1.2-beta.1`입니다. 이 PR은 해당 브랜치에 쌓이는 후속 변경이며, #7의 main 통합 이후 이 변경도 main으로 통합할 수 있습니다.

## 검증

`python3 tools/test_pdf_assembler.py`는 생산 Java 병합기를 직접 컴파일하고 별도 `-Xmx96m` JVM에서 실행합니다. 물리 순서가 다른 객체, 나중에 정의된 간접 stream Length, 폰트/페이지 참조, 괄호·hex 문자열과 바이너리 데이터를 검증합니다. 100 MiB 스트림 두 개의 SHA-256 보존, 잘못된 xref/루트/세대/증분/truncation 거절, 복사 중 취소와 페이지 writer 실패의 정리를 검사하며 `pypdf`로 별도 해석합니다.

새 CI는 기존 OCR/Python 검증과 전체 Gradle JVM 테스트 및 debug/androidTest APK 빌드를 수행합니다. Android API 23·35 에뮬레이터의 PDF 전용 `VectorPdfInstrumentation` 계측은 실제 `PdfDocument` 출력에 대해 다음을 확인합니다.

- 일반 필기 페이지에 전체 페이지 Image XObject가 없고 폰트 리소스가 존재함.
- 8종 브러시, 필압·기울기·형광펜, 곡선·회전과 한글의 네이티브 장면/출력 PDF 픽셀 비교.
- 다중 페이지 순서와 세로·가로 용지 치수.
- PDF 배경 합성 및 이미지 예산 초과 시 래스터 경로.
- 객체 렌더링 도중 취소, 미완성 PDF/임시 파일 삭제, 노트 객체 보존.

PDF 계측 APK는 `-PbadnoteVectorPdfTests=true`로 빌드합니다. API 24 이상의 PixelCopy 클래스를 참조하는 종합 계측 러너와 분리해 최소 API에서 실행합니다. 에뮬레이터 시스템 RAM은 2 GiB로 고정하며, Android 앱 전체 힙을 96 MiB로 제한한 검사가 아닙니다.

JVM의 200 MiB 결과는 **스트리밍 병합 엔진**의 힙 제한 검증입니다. 물리 Galaxy/S Pen 지연과 Android 앱 전체 메모리 성능은 별도 실기기 측정이 필요합니다.

## 제안 중 기존에 있는 구현과 다음 단계

현재 브랜치에는 `PageSpatialIndex`, 변경 객체 기반 `EditHistory`, 단축키, front-buffer 입력 경로, 우선순위/세대 기반 PDF 타일 작업, Room OCR 저장소와 실제 Task 완료를 따르는 OCR lease가 이미 있습니다. 같은 기능을 다시 추가하지 않았습니다.

다음 독립 리팩터링은 MainActivity의 문서·도구·뷰포트 상태를 생명주기와 분리하는 작업입니다. 저장 중 회전, 작업 복구, OCR 완료와 문서 전환 등 상태 전이를 먼저 검증한 뒤 ViewModel/StateFlow를 도입하는 것이 적절합니다. SAF 자동 백업과 듀얼 문서는 별도 기능 PR로 진행할 수 있습니다.
