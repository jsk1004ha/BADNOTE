# BADNOTE 네이티브 OCR 통합

## Beta 2 로컬 수정판의 OCR

`4.1.3-beta.2-local.1`은 공개 Beta 2 위의 로컬 변경이며 릴리스를 게시하지 않는다. 4.1.1 통합 계획·배포·기기 검증은 별도 보관 기록으로 옮겼다.

- 디지털 필기 입력은 줄 높이 128 단위와 여백으로 정규화하고 같은 단위의 `WritingArea`를 사용한다. 원본 좌표·획 순서·시간·capture는 바꾸지 않는다. 실제 앞 문장이 없는 경우 임의의 문맥을 넣지 않는다. [ML Kit 입력 권장 사항](https://developers.google.com/ml-kit/vision/digital-ink-recognition/android)을 따른다.
- 줄을 먼저 찾고 짧은 수평 획·분리된 작은 표시를 연결해, 마이너스나 한글 자모를 별도 문장으로 취급하는 오류를 줄인다.
- `mixed-review`/`ko-primary`/`en-primary`는 한국어·영어 실제 모델의 후보를 보존한다. 충분한 빈 수평 간격(줄 높이의 0.35배 이상)에서만 단어 영역을 나눈다. x 투영이 겹치는 획과 점은 분리를 막으며, 64개 단어 상한을 넘으면 전체 줄 처리로 돌아간다. 단어별 내부 capture/시간 순서를 유지한다. 엄격한 `ko`/`en`과 수식의 영어 토큰 경로는 이 분리를 사용하지 않는다.
- 한영 혼합 검토에서 한국어 모델의 한글은 유지하고, 양 모델의 top이 모두 Latin-only이면 영어 모델의 실제 후보를 우선한다. 이는 명시적인 언어 라우팅 정책이지 정확도 점수 비교나 정답 보장이 아니다. 단어 후보를 공간 순서로 조합한 결과는 `candidateKind=wordComposition`, `languageTag=mul`, `nativeRank=null`, `confidence=null`로 내부 저장한다. 사전·철자 치환·전체 줄 후보의 문자열 조각맞추기는 사용하지 않는다. 원래 후보와 source/bounds는 보존하지만 일반 결과 화면에는 후보·진단 목록을 노출하지 않는다.
- 수식은 별도 명령으로 처리한다. 실제 영어 디지털 잉크 후보와 필기의 상대 위치로 기본 숫자·연산자·괄호·분수·지수를 조합하며 여러 줄을 구분한다. 분수나 지수 사이의 실제 기준선 객체를 건너뛰어 합치지 않는다. 처리 가능한 후보가 있으면 지원하지 않는 다른 후보 하나 때문에 버리지 않는다. 지원 범위 밖 기호·구조에는 제한/검토 상태를 남기며 범용 LaTeX 또는 이미지 수식 인식으로 주장하지 않는다.
- 올가미 선택 변환과 수식 결과는 전체 페이지 자동 색인·기존 교정 데이터를 덮어쓰지 않는 임시 결과다. 사용자가 결과 텍스트를 검토·수정·복사·삽입하며 원본 획은 유지한다. 요청 이후 편집된 페이지에는 오래된 결과를 삽입하지 않는다. 수식 계산은 인식 결과와 별도로 실행한다.
- 입력 예산·실제 ML Kit Task 완료까지의 permit·취소·bitmap 수명·필기 중 자동 OCR 대기를 유지한다. 정책/레이아웃 fingerprint를 올려 이전 캐시를 새 정책 결과로 재사용하지 않는다. 모델의 첫 다운로드가 필요하며 오프라인 실패를 성공 결과로 대체하지 않는다.

### 검색·결과 UI와 큰 수식 입력

- 편집기 상단의 검색과 현재 페이지 OCR 버튼은 좁은 화면에서도 고정 표시한다. 문서 옵션의 중복 항목은 제거했다. 올가미 선택 OCR은 별도 동작이며 직접 OCR 버튼은 선택 여부와 무관하게 현재 페이지만 처리한다.
- 결과는 한 편집란에 출력한다. 같은 줄의 예산 분할은 공백으로, 다른 줄은 줄바꿈으로 연결한다. 편집한 공백·빈 줄을 전체 복사·교정 저장·단일 텍스트 객체 삽입에 그대로 사용한다. 전체 교정은 기존 테이블에 원본 입력 집합과 결합하고, 원본 획·영역 및 오래된 결과 적용 방지를 유지한다.
- 내부 ID·후보 순위·검토 코드·JSON 내보내기는 일반 OCR 화면에서 제거했다. 실제 부분 실패·취소·지원 범위 제한에 대한 사용자 안내는 유지한다.
- 문서 검색은 PDFium 일치 문자 사각형, OCR 단어 bounds, 직접 텍스트·수식 객체 위치를 반환한다. 정확한 단어 대응이 없는 OCR은 유효 영역을 사용하며, 좌표 없는 legacy·전체 교정에는 단어 사각형을 만들지 않는다. 강조는 페이지 좌표 overlay이며 확대·이동에 따라 움직이고 검색 변경·닫기·편집 때 해제한다.
- 수식은 원본으로 줄·분수·지수를 분석한 뒤 모델 입력만 높이 128로 정규화하고 0.35 단위 오차의 반복형 RDP로 조밀한 점을 줄인다. 원본 JSON·pen-up·획 순서·선택된 원본 점의 시간은 유지한다. SDK 입력은 512획·8,192점과 보수적 256KiB 예산을 모두 만족해야 한다. 안전한 빈 공간에서는 완전한 획 사이로 분할하며, 상세도 보존이 불가능하면 제한 상태를 남긴다. 원본 2,048획·64줄·128회 모델 요청 구조 한도는 유지한다.
- 모델 실패는 해당 줄에 격리한다. 다른 줄의 정상 결과는 복사·삽입할 수 있고, 수식 텍스트의 선택 부분만 계산할 수 있다. 범용 수학 OCR이나 무제한 입력 지원은 아니다.

### 이번 변경의 실행 확인

API 35 분리 Debug 앱에서 `documentSearchOnly`, `ocrUiOnly`(811dp·406dp), `ocrQuality`를 실행했다. 검색 검사는 실제 PDF의 반복 단어·두 열·90도 회전/crop·import, OCR 단어·교정·stale 및 직접 텍스트를 포함한다. UI는 직접 버튼·현재 페이지만 요청·정확한 복사·단일 삽입·undo·교정 검색·강조 해제·stale 거부·선택 수식 계산을 확인했다. 실제 단일 결과 화면은 `build/current-improvements/corrected/ocr-*-actual.png`에 보존한다.

큰 수식 실제 모델 회귀는 단일 숫자·분수·지수·여러 줄의 1×/4× 조밀 입력 8개를 모두 완료했다. 예산 내 payload와 원본 해시 불변을 확인했으며, 합성 fixture 결과를 사람 필기의 정확도나 모든 수식의 성공 보장으로 해석하지 않는다. 영수증은 `build/current-improvements/corrected/ocr-quality.json`의 `largeMathRegression`이다.

최초 계측에서 저장 전 숫자 표현으로 만든 fixture digest가 거부되고, 기존 raw 후보 probe가 영어 전용 수식 API에 한·영 두 모델을 요구하는 오류를 발견했다. 저장 후 snapshot과 원래 일반 인식 API로 각각 수정한 뒤 통과했다. 저장소 검증을 우회하거나 모델 누락 검사를 약화하지 않았다.

기존 PDF의 저장 문자열이 비어 있거나 글자마다 줄바꿈된 경우에도 원본의 실제 일치 범위를 조회한다. 실제 Type3 PDF에서 PDFium이 같은 기준선의 인접 glyph 사이에 generated CR/LF를 넣는 문제도 확인했다. 원본 glyph의 위치·각도·font·간격이 같은 줄의 인접 글자임을 뒷받침할 때만 generated CR/LF를 제외하고 원래 문자 인덱스로 검색한다. 명시적 공백·개행·다른 줄·떨어진 열은 합치지 않는다. 동일 실패 PDF의 18개 glyph 영역, 두 줄 비결합·명시적 공백 보존 회귀와 실제 앱 검색 강조를 통과했다. `pdf-search-highlight.png`가 화면 증거이며 기존 PDF/메타데이터는 재작성하지 않았다.

### 이전 로컬 수정판의 실행 검증과 해석

별도 API 35 에뮬레이터에서 실제 Task의 동시성·취소/실패 복구, 선택 결과의 전체 색인 비오염, 저장·교정·편집 세대와 필기 중 자동 OCR 대기를 실행했다. 접촉이 유지된 부하 검사에서 자동 OCR admitted/layout CPU/layout jobs는 모두 0이었다.

동일한 합성 필기 fixture를 원본 Beta 2와 수정본의 실제 ML Kit 모델에 재생한다. 이 검사는 구현·모델 연결과 특정 입력의 회귀 증거이며 실제 작성자·Galaxy 기기의 한국어/영어 정확도 표본이 아니다. 원시 모델 후보·정답·해시·출력은 `build/local-improvements/`의 영수증에 남긴다. 제공되지 않은 confidence를 만들어 인식률 향상으로 표시하지 않는다.

고정 fixture SHA-256: `e30eec5ba1eee2eb66b607d7001b6e4d03372a94e84b3f5bc5c44b638914f2ca`. 실행 영수증은 `baseline-receipt-text-only.json`과 `candidate-final-ocr-quality.json`이다. 두 앱에서 입력 해시가 같고 원본 획은 변경되지 않았다. 아래 `\n`은 줄바꿈이다.

| 의도한 합성 필기 | 공개 Beta 2 실제 출력 | 로컬 수정판 실제 출력 |
| --- | --- | --- |
| `한글` | `한글` | `한글` |
| `hello` | `hello` | `hello` |
| `한글 hello` | `한글hedCO` | `한글 hello` |
| `한글 hello\nhello` | `한글hedCO\nhedo` | `한글 hello\nhello` |
| 분수 `1/2` | `mathEngineUnavailable` | `((1)/(2))` |
| 지수 `2^3` | `mathEngineUnavailable` | `(2)^(3)` |
| `(1+2)` | `mathEngineUnavailable` | `(1+2)` |
| `1+2\n2^3` | `mathEngineUnavailable` | `1+2\n(2)^(3)` |

이는 작은 합성 입력에서의 실제 관측값일 뿐 정확도 백분율이 아니다. 별도 서명 앱에서 세로 선 두 개와 더하기를 직접 그린 `1+1`은 `I+I`로 인식됐다. UI는 검토 필요와 원래 후보를 표시했고 `1+1`로 직접 교정할 수 있었다. 이 모호한 글자를 자동으로 숫자에 치환하지 않는다.

단어별 실제 입력 계획의 timing을 캐시 키에 포함한다. 색상 등 인식 입력과 무관한 변경에서는 후보만 재사용하고 source identity는 현재 획에 다시 결합한다. 페이지 복제 시 단어·budget fragment의 ID와 source identity도 새 페이지에 맞춘다. 실제 저장소의 일반/분할 줄 복제 검사를 포함한 이전 `s5cOnly`가 통과했다. 64개 단어 한계의 검토 이유는 fallback·캐시에 유지하며 일반 UI에는 내부 코드를 표시하지 않는다.

Android 실제 UI에서 `1+1` 계산 시 `\frac`/`\sqrt` 정규식의 닫는 중괄호가 escape되지 않아 ICU `PatternSyntaxException`이 발생하는 기존 오류를 발견했다. literal 중괄호를 명시적으로 escape하고 패턴을 한 번만 컴파일하도록 수정했다. JVM 단위 검사와 별도로 Android `ocrOnly`에서 일반식·TeX 분수/제곱근·중첩 분수·지수를 계산했다. 실제 OCR 출력의 `((1)/(2)) → 0.5`, `(2)^(3) → 8`과 여러 줄 계산도 영수증에 기록했다.

서명 앱 UI에서는 올가미 선택 → 텍스트/수식 분리 메뉴 → 실제 단어 후보 선택 → 전체 문장 교정 → 클립보드 복사(붙여넣기로 값 확인) → 원래 위치 삽입을 실행했다. 삽입의 한 번 취소/복구와 앱 강제 종료 후 재실행에서 원본 4획과 삽입 텍스트가 보존됐다. 수식 결과 `I+I`를 사용자가 `1+1`로 고친 뒤 계산한 `1+1 = 2`도 실제 화면에서 확인했다. 영수증·화면은 `release-ocr-ui-before-math-fix.json` 및 `candidate-release-calculator-fixed.png` 등으로 수정 전 오류와 수정 후 결과를 구분한다.
