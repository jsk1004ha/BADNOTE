# 4.1.3 펜 입력 최적화 검증

**2026-10-27 검증 정정:** 이 문서의 과거 `HardwareRasterOracle` GPU 비교는 0×0 루트로 빈 이미지를 비교한 결함이 발견되어 근거에서 제외한다. 실제 창 스크린샷·소프트웨어 픽셀·원본 데이터 검사는 별도다. 검사 장치를 고쳐 수행한 결과와 local.3 진행 상태는 [필기 캐시 복구 기록](INK-LOCAL.3-KO.md)에 있다.

## Beta 2 기반 로컬 수정판

`4.1.3-beta.2-local.1` (415)의 기준은 공개 Beta 2 태그 `d6873da66a2fd76029bf89141d3af81606e9480f`다. 공개 Beta 1→Beta 2 수치·인증서·배포 검증은 별도 보관 기록으로 옮겼다. 아래는 이번 로컬 수정판의 기록이다.

### 수정한 경로

- `StylusButtonState`는 물리 버튼 상태와 현재 접촉의 지우개 상태를 분리한다. 버튼을 놓아도 현재 접촉을 마칠 때까지 지우고, UP 다음에는 현재 도구를 복원한다. 계속 누른 키 상태는 다음 접촉까지 보존하되 CANCEL/도구 초기화에서는 제거한다. 다른 포인터·마우스의 버튼 이벤트는 필기 위치를 바꾸지 않는다.
- `InkCanvasView`는 올가미 드래그 시작 때 원본과 표시 순서를 고정한다. MOVE에서는 누적 변위만 갱신하며, 선택/비선택 객체가 교차하는 표시 순서를 유지한다. UP에서 한 번 좌표를 확정하고 한 편집으로 저장한다. CANCEL은 원본·세대·히스토리를 바꾸지 않는다.
- 공간 검색과 bounds 캐시로 불필요한 객체 순회를 줄였다. 드래그 표본마다 JSON 문자열 왕복과 전체 객체 복사를 하지 않으며, 회전이 없는 객체의 렌더링에서도 불필요한 bounds/Canvas save를 피한다.
- 필압·시간·기울기·포인터·capture와 알 수 없는 JSON 필드, 선택되지 않은 잠긴/숨긴 객체는 보존한다. 입력 좌표 수를 줄여서 얻은 최적화가 아니다.

### 검증 조건과 제한

Android 15/API 35, x86_64, 1600×1000, density 213의 별도 AVD `badnote_beta2_local_verification` (`emulator-5582`)를 사용한다. 기준 앱은 공개 태그의 제품 코드 그대로 빌드하고 계측 코드만 추가했다. `build/local-improvements/`에 원본·수정본 실행 영수증과 APK 해시를 보존한다.

S Pen 접촉 계측에서 key/generic/MOVE 버튼 해제 뒤의 지우개 유지, 과거 표본, hover, 버튼을 누른 채 여러 접촉, 다른 마우스 이벤트 격리, 취소·도구 초기화와 한 접촉의 실행 취소/다시 실행을 확인했다. 별도 저장 검사는 원시 표본, Room 변경 단위 저장, 지우개·올가미와 실행 취소/다시 실행을 실행했다. 이 결과는 실제 삼성 기기의 버튼 드라이버·펜촉 지연 측정이 아니다.

올가미 부하는 선택된 512획 × 32점과 잠긴/숨긴 객체를 사용한다. MOVE당 현재/과거 표본은 총 4개다. 48 MOVE 원본 실행은 900초 안에 끝나지 않았다. 종료 전 main stack은 `JSONTokener → copyJson → ObjectChange.apply → InkCanvasView.movePoint`에 있었으며, 이를 성공한 p95나 개선율로 환산하지 않는다. 동일 512획을 유지한 12 MOVE 실행은 별도의 짧은 비교 조건이다.

12 MOVE 기준 실행도 전체 900초 제한을 넘었다. 준비 실행 1회는 저장·실행 취소·취소 검사까지 완료했으며, MOVE 경과 시간 p95 54,669.297ms, 중앙값 15,027.022ms, 최대 54,669.297ms, draw p95 12,942.356ms였다. 이는 준비 실행의 부분 기록이지 측정 3회의 중앙값이 아니다. 원시 기록은 `lasso-baseline-12-partial.json`, 제한 결과는 `lasso-baseline-12-timeout.json`이다. 완료된 동일 조건의 기준 3회가 없으므로 개선율을 제시하지 않는다.

좌표 검사는 독립적인 `원본 + 변위`를 기준으로 한다. 화면↔페이지 Float 왕복의 최대 허용 오차는 0.001 페이지 단위이고, 좌표 외 필드·잠긴/숨긴 객체·배열 순서·저장값과 메모리값·취소 결과는 정확히 일치해야 한다. 최초 문자열 전체 비교 실패의 실제 좌표 차이는 최대 x 0.00015/y 0.00066이었으며 원시 메타데이터 손실은 없었다. 좌표 오차를 숨기거나 객체 수를 줄여 통과시키지 않았다.

### 메모리와 표시 회귀

반복 부하의 두 번째 UP에서 192MiB heap 한계의 OOM을 실제로 발견했다. DOWN 원본 복제·UP 변환·apply 재복제·preview/history/page의 중복 소유를 줄였다. 드래그 원본은 변경하지 않고 빌리며, 새 변환 결과만 page에 채택한다. Undo/redo는 방어적 복사 후 새 revision을 부여하여 이미 저장 큐에 전달한 과거 delta를 변경하지 않는다. View close 시 소유 캐시를 해제한다. 계측 View는 open 중 실제 window에 붙여 비동기 page 배송을 마친 뒤 분리하고 trial 종료 때 close한다. 과거 View의 GC-root 누수 자체는 heap dump가 없어 입증하지 않았다.

수정 후 같은 512×32/48×4/준비 1회+측정 3회가 heap 확대·강제 GC 없이 통과했다. 원본 필드/NULL/순서/저장값, 한 번 취소/복구와 지연된 Room 저장 8개 publication의 revision 불변까지 확인했다. 관련 원시 기록은 `candidate-fixed-lasso-48.json`과 `.log`다.

브러시의 점별 smoothing에서는 렌더링에 쓰지 않는 vendor JSON tree 복사를 제거했다. 7종 브러시의 기존 산술·필압·테이퍼·선택적 각도와 JSON 수치 정규화를 유지한다. 실제 화면 검사는 1080×1600 세로 환경에서 수행했다. 기존 표시 검사의 y=900 페이지 표본이 가로 화면 밖으로 나간 실패는 좌표 검사를 약화하지 않고 화면 전제를 맞춰 해결했다.

- 실제 합성 화면: 반복 alpha raster 42건, 최신 snapshot 128건, commit 대기 중 다음 획, 연속 획·취소·undo/redo·clip·fallback·확대·surface 재생성·회전 통과.
- 부모 SurfaceView의 독립 PixelCopy는 status 3 (`ERROR_SOURCE_NO_DATA`)였다. 실제 합성 화면 픽셀 검사의 성공을 이 PixelCopy의 성공으로 바꾸어 기록하지 않는다.
- 10,000개 페이지 **메타데이터**와 60회 scroll/zoom, 480×640 software draw 부하에서 draw p95 582µs, 제스처 중 자동 OCR admitted 0. 실제 10,000페이지의 모든 콘텐츠를 동시에 렌더링한 결과가 아니다.

### 최종 올가미 수치와 산출물

확정 단계의 `InkGeometry.transform`에만 구조적 깊은 복사를 적용해 전체 객체 문자열 생성/escape/재파싱을 제거했다. 전역 `copyJson`은 바꾸지 않았다. 원본과 변환 결과의 중첩 소유권은 분리하며, Android/JVM의 기존 scalar writer/parser와 정수·Float·Double·signed zero·큰 수·NULL·문자열 정규화를 대조한다. 실제 Android에서도 Number class/Double bits·unknown metadata·배열 순서·원본 비변경·지연 저장 검사가 통과했다.

### 다획 필기·지우개와 PDF 확대 추가 개선

저장 명령을 최대 32객체의 안정적인 연속 run으로 재사용한다. 펜은 마지막 부분 run만 확장하고 지우개는 관련 run만 다시 기록한다. 공간 인덱스도 편집 delta로 갱신하며, 정확 충돌 검사에서 점별 JSON 복사를 제거했다. 이미지 경계·alpha·회전·올가미 순서와 원시 입력은 유지한다.

API 35 분리 Debug 앱의 `denseInkOnly`에서 2,048획×20점, 8회 펜/형광펜 접촉 및 획·정밀 지우개를 실행했다. 초기 2,049객체 명령 기록 뒤 펜 8회에서 44객체, 지우개 검사에서 203객체만 재기록했고 공간 인덱스 rebuild는 1회였다. 원시 필드·순서·보호 객체·분절·한 접촉 undo/redo/cancel·저장 delta와 검색 overlay 확대/해제 픽셀 검사를 통과했다.

입력 처리와 화면 그리기를 분리한 수치다. 물리 S Pen·GPU·전체 표시 지연을 측정하지 않았으며 즉시 표시를 보장하는 수치가 아니다. DOWN의 동기 capture 순번 예약과 저장 위치 갱신, visible scene 합성/raster 비용은 남는다. 최초 계측 OOM은 전체 JSON baseline을 여러 벌 보관하던 helper를 객체별 독립 문자열로 바꾼 뒤 동일 부하에서 사라졌다. 원래 예외의 stack이 없어 OOM 발생 위치는 확정하지 않는다. 부하 축소·heap 증가·강제 GC는 사용하지 않았다.

PDF는 전체 페이지 overview(최대 512×512)와 기존 해상도 타일을 bounded LRU 안에서 유지하고 준비된 고해상도로 덮어쓴다. viewport가 달라도 겹치는 요청을 공유하고 알림을 병합한다. `pdfZoomOnly`에서 실제 import/PdfRenderer, bucket 전환, 미방문 영역 pan, 요청 재사용, 해상도 전환, source 격리, Picture/bitmap 수명·close를 통과했다. 처음에는 미방문 영역 pan의 공백을 발견했으며 overview를 추가해 같은 검사를 통과했다. 실제 앱의 100%→125%→156%→195% 확대 화면도 확인했다.

관련 JVM 검사 68개/8 suites(실패·오류·skip 0), Debug/AndroidTest 빌드, S Pen 접촉 유지와 전면 표시 검사(42 raster·128 snapshot)도 통과했다. 전면 표시 검사는 기존 세로 화면 전제(1080×1600)를 사용했다. 전체 장시간 suite·release 빌드·물리 기기 검사는 이번 간소화 검증에 포함하지 않았다.

원시 기록과 화면: `build/current-improvements/corrected/`. 위 계측 당시에는 Debug만 빌드했고 release 산출물은 다시 빌드하지 않았다. 현재 최종 APK는 루트 `build/apk/`에 모은다. 2026-10-22 경로 정리에서 현재 소스의 Debug·Update·SideBySide APK를 다시 빌드했으며, 계측용 APK는 `build/apk/tests/`에 둔다.

### 다획 화면 캐시와 페이지 관리 후속 개선 — 이전 단계

확정된 화면을 256×256픽셀의 변경 불가능한 타일로 보관한다. 32객체 run 내부에서도 객체별 `Picture`와 실제 브러시 경계를 재사용한다. 펜 이동은 기존 획 재생 없이 화면 타일을 사용하고, 지우개는 이전·새 경계의 변경 영역에 걸친 객체만 다시 그린다. 한 프레임의 변경 타일은 합친 영역으로 한 번만 재생한다. 작업용 화면과 현재 타일의 픽셀 저장 한도는 합계 64MiB이며, 한도를 넘는 화면은 직접 그리기로 전환한다. 전면 화면이 참조할 수 있는 게시된 bitmap은 강제로 recycle하지 않는다.

타일별 좌표 이동과 잘라내기가 회전·반투명 획의 경계 픽셀을 바꾸는 문제가 실제 검사에서 발생했다. 전체 화면의 좌표 변환·clip을 유지한 작업 화면에서 그린 뒤 타일을 복사하도록 수정했다. 정확한 픽셀 비교를 완화하지 않았다. 저장 경로는 현재 ID·순서를 한 번 조회하고 실제 바뀐 순서만 갱신한다. 원자적 저장과 영속 capture 순번 예약은 유지하며, 완료 시 전체 객체를 반복 탐색하던 작업도 줄였다.

API 35 에뮬레이터, 1080×1600 화면에서 기존 2,048획×20점과 8회 펜/형광펜 접촉을 유지하고, 회전·반투명 브러시 7개를 추가한 `denseInkOnly`를 실행했다.

| --- | ---: |

펜 MOVE 중 기존 객체 재생은 0회였고 펜·지우개 계측 구간의 전체 캐시 재생성도 0회였다. MOVE와 UP 후 그리기를 합친 기존 형식의 p95는 펜 58.886ms, 지우개 58.575ms였다. 앞 절의 과거 계측과는 추가 브러시·에뮬레이터 부하가 달라 동일 조건의 전후 비율로 해석하지 않는다. 최초 로딩·전체 화면 재생성 및 UP 비용은 남는다. 물리 S Pen·GPU·종단 표시 지연을 측정한 수치가 아니며 모든 입력의 즉시 표시를 보장하지 않는다.

원시 입력·historical sample·순서·보호 객체·지우개 분절·접촉 중 지우기 픽셀·한 접촉 undo/redo/cancel·저장 후 재열기·capture 순번·트랜잭션 rollback을 통과했다. 실제 PNG의 alpha/겹침 순서와 캐시 사용 중 비동기 PNG/PDF 도착, 확대/복귀도 확인했다. 최종 APK의 실제 문서 화면에서 저장된 다획 노트가 표시되는 것도 확인했다.

페이지 관리는 360dp·811dp·1202dp에서 실제 버튼 입력과 화면 캡처로 확인했다. 새 페이지, 썸네일/번호 이동, 대기 중인 저장을 반영한 복제, 앞뒤 순서 변경, 삭제 취소/확인, 중간·마지막 쪽 삭제 후 선택, 재열기 위치, 마지막 한 쪽 보호를 통과했다. `페이지 관리` 진입점과 하단의 `새 페이지`·`페이지 삭제` 버튼은 작은 화면에서도 표시된다.

최종 앱에서 S Pen 접촉 유지 검사와 전면 표시 검사(42개 정확 raster 비교·128개 snapshot), 360dp 페이지 관리 흐름을 다시 통과했다. 후속 계측 초기에 서재 준비 작업이 남아 편집기 로딩 제한에 걸렸다. 검증 코드에서만 executor 작업·UI 프레임·대기 중 썸네일/저장의 완료를 별도 준비 단계로 기다리도록 수정했고, 예상 페이지 ID와 30초 편집기 준비 조건은 유지했다. 앱 데이터 삭제·로딩 오류 무시·편집기 재시도로 우회하지 않았다.

Debug/AndroidTest와 Update/SideBySide release를 빌드했고, 최종 앱 APK 3개의 패키지·버전·서명·ZIP CRC·16KiB 정렬·고정 PDFium 일치를 확인했다. 전체 JVM·장시간 계측 suite는 실행하지 않았다. 원시 결과·화면·APK 검증 JSON은 `build/ink-page-improvements/`에, 설치 파일은 `build/apk/`에 있다.

### 고밀도 필기·다페이지·드래그 정렬 개선

#### 변경한 입력·표시·저장 경로

- 긴 필기의 전면 게시에는 불변 청크를 사용한다. 점이 추가되어도 변하지 않는 경로와 테이퍼가 완전히 안정된 몸통 명령만 재사용한다. 머리·꼬리는 현재 전체 점 수로 다시 계산하며, 연필의 전체 점 수·간격·난수 의존성과 두 점에서 세 점으로 바뀌는 경우를 보존한다.
- 확정된 장면 위의 순수 마지막 획 추가는 기존 장면을 다시 재생하지 않고 합성한다. 다른 편집의 부분 손상 뒤에도 완전한 기준 화면을 유지한다. alpha·multiply·회전·이미지의 겹침 순서를 바꾸지 않는다.
- 지우개는 한 MotionEvent의 과거 표본과 원형 경로를 불변 입력으로 묶고, 획별 primitive 선분 BVH에서 전체 이동 범위의 후보를 한 번 조회한다. 큰 획의 경계 상자와 겹친다는 이유만으로 모든 선분을 각 원마다 검사하지 않는다. BVH 배열은 쪽당 4MiB로 제한한다. 객체마다 기존 순서의 정확한 원형 절단을 적용한 뒤 한 번 반영하고, 좌표·절단점 descriptor와 순서 인덱스를 재사용하여 최종 결과에 필요한 JSON만 만든다. Float 잔차 구간으로 확실한 비충돌 선분을 먼저 제외하되, 가능한 충돌은 기존 투영·hypot·이차식·접선·중복 표본 규칙으로 판정한다.
- 많은 격자 셀에 걸치는 큰 획은 기존의 넓은 객체 집합으로 분리한다. 삭제·분절마다 같은 ID를 수십~수백 개 셀에서 반복 제거·삽입하지 않으며, 조회의 경계·회전·정확 충돌 판정은 그대로 유지한다.
- API 29 이상에서는 변경된 **현재** 장면을 불변 RenderNode로 표시한다. 지우개가 움직이는 동안 이전 비트맵을 대신 보여 주지 않는다. 정확한 전체 화면 좌표·clip을 가진 Picture는 UI에서 기록하고, 접촉이 끝난 뒤 최신 요청만 남기는 단일 작업자에서 비트맵을 만든다. 작업자는 BackgroundLoader를 건드리지 않으며 장면·뷰포트·attach 세대가 달라진 결과는 버린다. 오래된 전면 장면도 다시 표시하지 않는다.
- 픽셀 저장은 기준 화면·타일·작업물·이전 게시물의 여유를 포함해 픽셀당 32바이트, 최대 128MiB로 입장을 제한한다. 명령 캐시는 별도 한도를 적용한다. 한도를 넘거나 해당 하드웨어 API를 쓸 수 없는 경우의 직접 그리기 경로는 유지한다. 게시된 비트맵을 강제로 recycle하지 않는다.
- 저장 JSON 생성은 SQLite 쓰기 트랜잭션 밖으로 옮겼다. 영속 capture 순번 예약은 동기식으로 유지한다. 실행 취소의 정확한 크기 계산·예산 적용은 별도 작업자로 옮기고, 대기 중인 항목의 undo/redo·취소·수명을 보존한다.
- 선택 페이지 읽기·준비와 썸네일 그리기를 분리하고, 선택 요청 우선순위·취소·세대 검사를 적용했다. 메타데이터와 쪽 수를 묶어서 조회하며, 페이지 목록은 RecyclerView 셀을 재사용한다.

#### 실제 화면과 데이터 검증

API 35, x86_64, SwiftShader 에뮬레이터 `badnote_native_api35`의 분리 Debug 앱을 사용했다. 필기 화면은 1080×1600/density 213, 힙 한도는 192MiB다. 기능 설정을 임의로 바꾸지 않았다. 계측 당시 자동 OCR·길게 그려 도형 만들기·낙서 지우기는 꺼져 있었고 스타일러스 전용·연속 페이지는 켜져 있었다. 꺼진 기능의 동시 부하까지 검증한 것으로 해석하지 않는다.

- 360dp·1202dp에서 우측 끝의 동등한 48dp 아이콘, 실제 길게 누르기·양방향 드래그·삽입 위치·가장자리 자동 스크롤·홀수 마지막 행·제자리/바깥 놓기·취소·닫기·접근성 드래그를 확인했다. 저장 대기 중 재정렬, 선택 페이지의 undo/redo, 오래된 목록의 거부, 재열기, 북마크·복제·삭제·마지막 쪽 보호도 통과했다. 기존 하단 페이지 메뉴와 앞/뒤 이동 항목은 제거했다.
- 320쪽 각각 96획×32점, 총 983,040개 원시 표본을 저장한 문서에서 실제 썸네일·페이지 이동·편집 직후 이동·전체 저장 순서·재열기를 통과했다. 최종 APK에서 최초 선택 페이지 준비는 718.141ms, 이후 선택 콘텐츠 준비는 74.690~1181.747ms였다. 화면 관찰용 캡처 비용과 구분한 값이며 페이지 전환이 언제나 즉각적인 것은 아니다. 실제 유지된 페이지는 2~3쪽, 원시 표본은 최대 9,227개로 모든 쪽을 동시에 올리지 않았다. 최종 기록은 `many-pages-delivery.log`다.
- 실제 하드웨어 버퍼의 전면·일반 브러시 렌더링 3,248건, 기존 정확 소프트웨어 raster 42건·긴 획 378건·불변 snapshot 128건을 통과했다. 별도의 새 renderer와 fence 완료 뒤의 sRGB 픽셀을 비교했다. 펜/지우개 전환·같은 접촉의 버튼 해제·과거 표본·취소·undo/redo도 통과했다.
- 전체 화면을 덮는 2,048획×64점, 총 131,072개 원시 표본과 4,098점의 긴 추가 획을 사용했다. 반복 접촉, 획/정밀 지우개, 한 접촉의 취소·undo/redo·원시 필드·순서·영속 저장을 확인했다. 별도의 현재 장면 GPU 비교는 지우개 MOVE와 같은 UI dispatch에서 기록하여 새 비트맵 완료로 문제를 가리지 않는다. GPU 픽셀 검사를 하는 구간은 성능 구간과 구분한다.
- 최종 집중 JVM 검사 73개/9 suites는 실패·오류·건너뜀 0이었다. Debug/AndroidTest·Update·SideBySide를 다시 빌드하고, 앱 APK 세 개의 패키지·버전·서명·ZIP CRC·16KiB ZIP/64비트 ELF 정렬·고정 PDFium 일치를 확인했다. 전체 장시간 suite·실물 S Pen·API 23 실행 검사는 하지 않았다.

#### 최종 고밀도 입력 계측

아래의 초기 통합본은 이번 작업 중 추가 병목 수정 전의 `filled-ink-final.log`, 최종 APK는 `filled-ink-delivery.log`다. 공개 원본 APK와의 비교가 아니다. 동일한 131,072점·4,098점 입력 부하의 개별 실행이며, 최종 실행에는 별도 GPU 픽셀 검사도 추가되어 엄격한 반복 A/B 개선율로 해석하지 않는다.

**완전한 무지연 목표를 달성했다는 결과는 아니다.** 최악 밀도의 정밀 지우개는 입력 처리 자체에도 약 203ms가 남는다. WindowTotal은 앱 윈도우의 FrameMetrics이며 별도 전면 Surface의 물리 표시 지연이 아니다. GPU oracle readback과 경계 프레임이 섞일 수 있는 지우개 구간의 WindowTotal은 전후 비교 지표로 쓰지 않는다. 실제 S Pen·실물 GPU에서 펜촉부터 화면까지의 지연은 측정하지 않았다.

최종 실행은 보이는 종이 내부 1,087,992픽셀 중 911,035픽셀(83.7%)에 잉크가 있고, 원시 표본을 줄이지 않았다. 최종 2,703객체의 필드·순서·저장을 확인했다. 마지막 Java 힙 사용량은 124,422,032바이트, 힙 한도는 201,326,592바이트로 확대하지 않았다. 최종 결과·설치 파일 해시·검증 범위는 `verification.json`에 정리했다.

측정·화면·단계별 진단 자료는 `build/dense-pages-drag-improvements/`, 설치 파일은 `build/apk/`에 있다. 진단용 method sampling 코드는 제거했다. 입력 처리 시간, View 그리기, GPU 비교의 readback 비용, screenshot 관찰 간격은 서로 다른 값이며 물리 펜촉부터 표시까지의 지연으로 합치거나 “항상 즉시 표시”를 보장하지 않는다.
